# GitHub Configuration Guide - Per-SOW Setup

## Overview

The GitHub Configuration feature allows you to set up separate GitHub repositories, labels, milestones, and automation for each Statement of Work (SOW). This enables proper tracking and management of obligations, deliverables, and compliance requirements on a per-project basis.

## Key Features

### 1. **Per-SOW Configuration**
- Each SOW can have its own GitHub repository configuration
- Separate repositories for pre-acceptance and post-approval workflows
- Custom labels, milestones, and issue templates per SOW

### 2. **Workflow Stages**
- **Pre-Acceptance Repository**: Used for SOW review, SLA negotiation, and acceptance criteria before approval
- **Delivery Repository**: Used for approved delivery execution, implementation tracking, and SLA-bound work
- **Default Repository**: Fallback repository if stage-specific repos are not configured

### 3. **Automated Resource Creation**
- SOW-specific labels with custom colors and descriptions
- Milestone creation for tracking deliverables
- Auto-generated issues for obligations and reviews
- Issue templates with SOW-specific prefixes

## Configuration Workflow

### Step 1: Select SOW

1. Navigate to **GitHub Configuration** from the sidebar
2. View all available SOWs in your system
3. Click on the SOW card you want to configure
4. The selected SOW will be highlighted in green

### Step 2: Team Information

Configure the team details for the selected SOW:

**Required Fields:**
- **Project Manager**: Format: `Name <email@example.com>`
- **Tech Lead**: Format: `Name <email@example.com>`
- **Team Size**: Number of team members
- **Slack Workspace**: Your Slack workspace ID

**Key Stakeholders:**
- Add stakeholder emails one by one
- These will receive notifications for important events
- Can be removed by clicking the X on the chip

**Example:**
```
Project Manager: John Smith <john.smith@acme.com>
Tech Lead: Jane Doe <jane.doe@acme.com>
Team Size: 5
Slack Workspace: acme-corp
Key Stakeholders:
  - stakeholder1@acme.com
  - stakeholder2@acme.com
```

### Step 3: GitHub Repositories

Configure the GitHub repositories for different workflow stages:

**Default Repository:**
- Format: `owner/repository-name`
- Example: `acme-corp/platform-migration`
- Used as fallback if stage-specific repos are not configured

**Pre-Acceptance Repository (Optional):**
- Used before SOW approval
- Tracks review issues, SLA negotiations, acceptance criteria
- Example: `acme-corp/sow-reviews`
- Leave empty to use default repository

**Delivery Repository (Optional):**
- Used after SOW approval
- Tracks implementation, delivery execution, SLA-bound work
- Example: `acme-corp/delivery-tracking`
- Leave empty to use default repository

**Workflow Example:**
```
Default: acme-corp/platform-migration
Pre-Acceptance: acme-corp/sow-reviews (for negotiation phase)
Delivery: acme-corp/platform-migration (for execution phase)
```

### Step 4: Review & Apply

Review the generated configuration:

**Repository Configuration:**
- Default repository details
- Pre-acceptance repository (if configured)
- Delivery repository (if configured)
- Milestone name

**Labels (Auto-Generated):**
The system creates SOW-specific labels with the format `{sow-id}-{label-type}`:

| Label | Color | Purpose |
|-------|-------|---------|
| `{sow-id}-sla-critical` | Red (#d73a4a) | Critical SLA obligations |
| `{sow-id}-sla-high` | Orange (#ff6b6b) | High priority SLA obligations |
| `{sow-id}-sla-medium` | Yellow (#fbca04) | Medium priority SLA obligations |
| `{sow-id}-scope-creep` | Pink (#f9d0c4) | Potential scope creep detected |
| `{sow-id}-penalty-risk` | Dark Red (#d93f0b) | Penalty risk for obligations |
| `{sow-id}-milestone` | Green (#0e8a16) | Milestone tracking |
| `{sow-id}-compliance` | Blue (#1d76db) | Compliance requirements |

**Automation Settings:**
- ✅ Create Labels: Automatically create/sync SOW-specific labels
- ✅ Create Milestone: Create milestone for the SOW
- ✅ Auto-create Obligation Issues: Generate issues for SOW obligations
- ✅ Auto-create Review Issue: Generate pre-delivery review issue

**Apply Configuration:**
Click "Apply Configuration" to create resources in GitHub. This will:
1. Create all SOW-specific labels in the repository
2. Create a milestone for tracking deliverables
3. Generate issues for obligations and reviews
4. Save configuration to the database

## Prerequisites

### GitHub Token Configuration

Before using the GitHub Configuration feature, you need to configure your GitHub Personal Access Token:

**Option 1: Environment Variable**
```bash
export GITHUB_TOKEN="ghp_your_token_here"
```

**Option 2: Database Configuration (Recommended)**
Store the token in the database via the Settings API:
```bash
curl -X POST http://localhost:8000/api/v1/settings/save \
  -H "Content-Type: application/json" \
  -d '{
    "github_token": "ghp_your_token_here"
  }'
```

**Required Token Permissions:**
- `repo` - Full control of private repositories
- `write:org` - Read and write org and team membership
- `admin:repo_hook` - Full control of repository hooks

**Creating a GitHub Token:**
1. Go to GitHub Settings → Developer settings → Personal access tokens
2. Click "Generate new token (classic)"
3. Select the required scopes listed above
4. Copy the token and save it securely

### Repository Permissions

Ensure you have:
- Admin access to the target repositories
- Permission to create labels, milestones, and issues
- Permission to assign issues to team members

## Best Practices

### 1. **Repository Structure**
```
Pre-Acceptance Repo (sow-reviews):
- Used for: Contract review, SLA negotiation, acceptance criteria
- Issues: Review tasks, clarification requests, approval gates

Delivery Repo (project-delivery):
- Used for: Implementation, delivery execution, SLA tracking
- Issues: Development tasks, deliverables, milestones
```

### 2. **Label Naming Convention**
- Always use SOW ID as prefix: `{sow-id}-{label-type}`
- Keeps labels organized when multiple SOWs share a repository
- Easy to filter issues by SOW

### 3. **Team Configuration**
- Add all key stakeholders to receive notifications
- Use proper email format: `Name <email@example.com>`
- Keep team size accurate for resource planning

### 4. **Milestone Management**
- One milestone per SOW for tracking all deliverables
- Milestone name format: `{SOW-ID} Deliverables`
- Close milestone when SOW is completed

### 5. **Issue Templates**
- Title prefix helps identify SOW-related issues
- Body intro provides context for auto-generated issues
- Default labels ensure proper categorization

## Troubleshooting

### Issue: "GitHub token not configured"
**Solution:** Configure your GitHub token using one of the methods in Prerequisites section.

### Issue: "Failed to create labels"
**Possible Causes:**
- Insufficient repository permissions
- Labels already exist (this is usually OK)
- Invalid repository owner/name

**Solution:** 
- Verify repository access
- Check repository name format: `owner/repo`
- Existing labels will be skipped automatically

### Issue: "Failed to create issues"
**Possible Causes:**
- Invalid assignee usernames
- Repository doesn't exist
- Insufficient permissions

**Solution:**
- Verify assignee GitHub usernames
- Ensure repository exists and is accessible
- Check token permissions

### Issue: "Configuration not saved"
**Possible Causes:**
- Database connection issues
- Invalid SOW ID

**Solution:**
- Check backend logs
- Verify SOW exists in the system
- Ensure database is running

## API Endpoints

The GitHub Configuration feature uses these API endpoints:

### Generate Configuration
```http
POST /api/v1/integrations/configure
Content-Type: application/json

{
  "sow_id": "SOW-2024-ACME-001",
  "team_info": {
    "project_manager": "John Smith <john.smith@acme.com>",
    "tech_lead": "Jane Doe <jane.doe@acme.com>",
    "team_size": 5,
    "github_repo": "acme-corp/platform-migration",
    "pre_acceptance_github_repo": "acme-corp/sow-reviews",
    "delivery_github_repo": "acme-corp/platform-migration",
    "slack_workspace": "acme-corp",
    "key_stakeholders": ["stakeholder@acme.com"]
  }
}
```

### Apply Configuration
```http
POST /api/v1/integrations/apply/{sow_id}
Content-Type: application/json

{
  "sow_id": "SOW-2024-ACME-001",
  "team_info": {...},
  "github": {...},
  "slack": null,
  "outlook": null
}
```

### Get Configuration
```http
GET /api/v1/integrations/{sow_id}
```

### Delete Configuration
```http
DELETE /api/v1/integrations/{sow_id}
```

## Integration with Live Monitoring

Once GitHub is configured for an SOW:

1. **Compliance Agent** monitors GitHub velocity and issue status
2. **Contract Agent** tracks obligation completion via GitHub issues
3. **Risk Agent** identifies penalty risks from overdue issues
4. **Forecast Agent** predicts delivery dates based on GitHub activity

The Live Monitoring dashboard will show real-time GitHub metrics for configured SOWs.

## Example Workflow

### Scenario: New SOW Approval

**Step 1: Pre-Acceptance Phase**
1. SOW received: `SOW-2024-ACME-001`
2. Configure GitHub with pre-acceptance repo: `acme-corp/sow-reviews`
3. System creates review issues for:
   - SLA negotiation
   - Acceptance criteria validation
   - Commercial terms review

**Step 2: SOW Approved**
1. Update configuration to use delivery repo: `acme-corp/platform-migration`
2. System creates delivery issues for:
   - Phase 1 Database Migration (Critical SLA)
   - UAT Sign-off Document (High SLA)
   - Pre-delivery review

**Step 3: Delivery Execution**
1. Team works on issues in delivery repo
2. Compliance Agent monitors progress
3. Risk Agent alerts on approaching deadlines
4. Forecast Agent predicts completion dates

**Step 4: SOW Completion**
1. All issues closed
2. Milestone marked complete
3. Configuration archived for reference
